# WindAgent: короткие ответы жюри

Используйте ответы как опору для разговора. Числа относятся к сохранённым артефактам репозитория; они не доказывают будущую точность или финансовую экономию.

**Состояние источников:** текущая валидация имеет `generated_at_utc = 2026-09-23T10:44:42Z` в [metrics.json](../../outputs/shelek/validation/metrics.json). Блок метрик README ещё содержит прежние результаты. Сохранённые февральские выпуски и сабмит не пересчитаны после обновления модели. Например, [выпуск 01.02](../../outputs/shelek/runs/2026-02-01_0000/run.json) имеет `created_at_utc = 2026-09-23T10:05:53Z`. Ниже показатели текущей валидации и примеры прежнего расчёта названы отдельно.

**Какую задачу вы решаете и для кого?**

Оператору ВЭС и диспетчеру нужен почасовой график выработки, чтобы планировать подачу и резервы. WindAgent собирает доступные прогнозы погоды, проверяет их, рассчитывает выработку и неопределённость, публикует результат и пересматривает его при обновлении погоды. Бизнес-гипотеза — уменьшить ошибки планирования и ручную работу. Денежный эффект пока не измерен: для расчёта нужны тарифы небалансов, номинальная мощность и операционный пилот.

**Какой главный результат можно назвать?**

На текущей walk-forward валидации MAE прогноза на сутки вперёд составляет **0.168** в нормированных единицах мощности. Это на **11.3%** ниже ошибки кривой мощности по лучшей погодной модели. Это снижение ошибки, а не процент «точности» и не оценка экономии. Источник: [metrics.json](../../outputs/shelek/validation/metrics.json), `by_product.day_ahead.model.mae`, `skill_pct.day_ahead_vs_nwp_powercurve`.

**С чем сравнивали модель?**

| Метод | MAE на сутки вперёд | Снижение MAE нашей модели |
|---|---:|---:|
| WindAgent | 0.1680 | — |
| Кривая мощности по лучшей NWP-модели | 0.1894 | 11.3% |
| Климатология: месяц × час | 0.3249 | 48.3% |
| Персистентность: последний доступный час | 0.3680 | 54.3% |

Источник всей таблицы: [metrics.json](../../outputs/shelek/validation/metrics.json), `by_product.day_ahead.{model,nwp_powercurve,climatology,persistence}.mae`, `skill_pct.day_ahead_vs_*`. Снижение считается как `(MAE бейзлайна − MAE модели) / MAE бейзлайна`. Число валидных наблюдений различается: у модели **2869**, у персистентности **2836** (`by_product.day_ahead.{model,persistence}.n`). Поэтому эти агрегаты не следует называть сравнением на полностью одинаковом наборе часов.

**Как проверяли качество без случайного перемешивания прошлого и будущего?**

Walk-forward: перед каждым месяцем обучаемся на предшествующих данных, затем воспроизводим ежедневные выпуски с историческим ограничением доступности погоды. В отчёте **123 выпуска** за **октябрь 2025 — январь 2026**. Источник: [metrics.json](../../outputs/shelek/validation/metrics.json), `validation.n_issues`, `validation.folds`, `validation.method`. Это историческая проверка на данной площадке; вывод о качестве на других площадках требует отдельного эксперимента.

**Что означает ошибка 0.168: проценты, МВт или энергия?**

Это средняя абсолютная ошибка нормированной почасовой мощности на шкале **0–1**. В данном кейсе «ВЭС» — среднее **двух турбин**, а не сумма в МВт. Источники: [metrics.json](../../outputs/shelek/validation/metrics.json), `by_product.day_ahead.model.mae`; [блок METRICS в README](../../README.md#2-краткое-описание), вводная строка валидации. Без номинальной мощности переводить результат в МВт, МВт·ч и деньги нельзя.

**Чем отличаются горизонт, сутки вперёд и тестовый период?**

Сохранённый выпуск охватывает **48 часов**; сабмит содержит только **lead_h 24–47**, то есть следующие календарные сутки по времени данных. В нём **672 строки**: почасовые цели с **01.02.2026 00:00** до **28.02.2026 23:00**. Источники: [run.json выпуска 01.02](../../outputs/shelek/runs/2026-02-01_0000/run.json), `horizon_h`; [submission_day_ahead.csv](../../outputs/shelek/test_period/submission_day_ahead.csv), число строк без заголовка, минимум/максимум `lead_h` и `target_time_data_clock`. По [контракту](../CONTRACTS.md#schema-s-submission_day_aheadcsv-jury-facing) сабмит использует первоначальную версию выпуска. Сейчас это сохранённый набор предыдущего расчёта, его обновление вслед за моделью ещё требуется.

**Какая точность получилась в феврале?**

Пока неизвестна: фактической выработки за февраль в предоставленных данных нет. Публикуемые метрики качества относятся к исторической валидации. Например, [run.json выпуска 01.02](../../outputs/shelek/runs/2026-02-01_0000/run.json) содержит `actuals_available=false`, `errors=null`; [metrics.json](../../outputs/shelek/validation/metrics.json), `validation.last_observation_utc`, заканчивает факт на **31.01.2026 17:00 UTC**. После получения факта предусмотрена команда `evaluate`.

**Тогда откуда пост-проверка с MAE около 0.190?**

Она относится только к внутрисуточной части сохранённого выпуска **31.01**, где есть **24 часа** факта. Точное MAE составляет **0.1901**. Это результат предыдущего расчёта, не февральская метрика и не day-ahead оценка всего тестового периода. Источник: [run.json выпуска 31.01](../../outputs/shelek/runs/2026-01-31_0000/run.json), `errors.hours`, `errors.mae`, `errors.version`, `errors.note`. Сверка сделана после публикации; факт не передавался агенту для построения этого прогноза. Новому расчёту нужна собственная пост-проверка.

**Как исключаете утечку будущей погоды и фактической выработки?**

Правило as-of допускает погодный прогон только после его расчётного времени публикации: `init_time + publication_delay ≤ as_of`. Такое же правило используется в обучении; модель выбирается с допустимым cutoff, наблюдения SCADA берутся из прошлого. Ограничения задаются инструментами, LLM не может запросить будущий факт. Проверяемые поля выпуска — `issue_time_utc`, `forecast_model`, `versions[].as_of_utc`, `runs_used` в [run.json](../../outputs/shelek/runs/2026-02-01_0000/run.json). Оговорка: исторические задержки публикации оцениваются консервативно, а не восстановлены по журналу каждой фактической публикации.

**Почему у вас необычные часы?**

Для исходного регистратора принят фиксированный **UTC+6**; смешивать его с официальным временем нельзя. В примере выпуск **01.02.2026 00:00** по данным соответствует **31.01.2026 18:00 UTC**. Источники: [блок METRICS в README](../../README.md#2-краткое-описание), строка «Часы SCADA»; [run.json](../../outputs/shelek/runs/2026-02-01_0000/run.json), `issue_time_data_clock`, `issue_time_utc`. В сабмите явно разделены `target_time_data_clock`, `target_time_utc`, `target_time_kz_official`. Вывод о часах основан на статистических проверках, а не на документации регистратора.

**Зачем LLM, если прогноз считает обычная модель?**

Численные значения рассчитывает ML-модель: кривые мощности и gradient boosting. LLM управляет инструментами, реагирует на флаги качества, решает о пересчёте и формирует объяснение. Он не придумывает значения мощности; выбор набора погодных моделей может косвенно менять расчёт. В сохранённом [run.json](../../outputs/shelek/runs/2026-02-01_0000/run.json) указаны `policy=llm`, `provider=openai`, `model=gpt-5.4-mini`. При недоступности LLM предусмотрена политика правил с теми же инструментами.

**Что доказывает агентный цикл, кроме красивого текста?**

Есть опубликованные версии, их время и причина пересчёта. Например, у сохранённого выпуска **01.02** новая версия рассчитана через **6 часов** из-за новых погодных прогонов; средняя абсолютная разница с первоначальной версией составляет **0.0242**. Источник: [run.json](../../outputs/shelek/runs/2026-02-01_0000/run.json), разность `versions[1].as_of_utc − versions[0].as_of_utc`, `versions[1].reason`, `kpis.revision_mae_v2_vs_v1`. В сохранённом тестовом наборе **29 выпусков и 58 версий**. Источник: файлы `outputs/shelek/runs/*/run.json` в [каталоге выпусков](../../outputs/shelek/runs/), число файлов и сумма длин `versions`. Это свидетельства предыдущего расчёта. Разница версий показывает пересмотр, а не улучшение точности: для этого нужен факт.

**Демонстрация работает без интернета и API-ключа?**

Исторический расчёт можно запустить из погодного кэша с `--offline --policy rules`; интерфейс также читает сохранённые результаты. Сохранённые исходные выпуски содержат `policy=llm` и `weather_source=live`, например [run.json](../../outputs/shelek/runs/2026-02-01_0000/run.json), поэтому не следует представлять их как результат офлайн-запуска. Для текущей погоды и живого LLM требуется соответствующий доступ. Текущий [контракт](../CONTRACTS.md) сохраняет одиночный `forecast --issue` и запуск из интерфейса в `adhoc/<issue_id>/`, бэктест в `runs/<issue_id>/`; корень результатов задаётся переменной `WINDAGENT_OUTPUTS_DIR`.

**Совпадёт ли новый расчёт со старым сабмитом?**

Сейчас это нельзя обещать. Модель и валидация обновились, а сохранённый февральский набор остался прежним. Перед утверждением о совпадении нужно заново выполнить бэктест в отдельном каталоге и сравнить результаты. Возможность офлайн-расчёта сама по себе не подтверждает численную идентичность старому файлу. Даты формирования разных снимков указаны в начале этой памятки.

**Насколько надёжны P10–P90? Почему встречаются разные значения покрытия?**

Это разные срезы, их нужно называть вместе с периодом:

| Срез | До калибровки | После калибровки |
|---|---:|---:|
| Весь day-ahead набор валидации, сырые интервалы | 0.716 | Не заявляем по этому полю |
| Месяцы подбора: октябрь–декабрь 2025 | 0.717 | 0.800 |
| Отложенная проверка: январь 2026 | 0.713 | 0.799 |

Коэффициент расширения **k=1.07** подобран на первых месяцах, целевое покрытие составляет **0.80**. Источник всех чисел и периодов: [metrics.json](../../outputs/shelek/validation/metrics.json), `intervals.day_ahead.coverage_p10_p90`, `interval_calibration.{fitted_on_months,check_month,coverage_fit_before,coverage_fit_after,coverage_check_before,coverage_check_after,k,target_coverage}`. Январский результат близок к цели и немного ниже неё. Покрытие показывает долю фактов внутри интервала; это не гарантия для каждого часа и не измерение на феврале. Квантили ВЭС агрегируются приближённо, как средние квантилей турбин. Старые значения из README не использовать для этой проверки.

**Что даёт коррекция по свежей SCADA?**

В текущей валидации внутрисуточная MAE базовой модели составляет **0.1566**, с коррекцией **0.1530**. Источник: [metrics.json](../../outputs/shelek/validation/metrics.json), `by_product.intraday.model.mae`, `by_product.intraday.model_with_nowcast.mae`. В отчёте выбран **tau = 2 часа**, коррекция применяется при возрасте SCADA не более **2 часов**. Источник: `nowcast.tau_used_h`, `nowcast.note`. Это внутрисуточный результат, его нельзя выдавать за улучшение прогноза на следующие сутки или результат на неизвестном феврале.

**Можно ли перенести модель на новую турбину или новую ВЭС?**

Проверен ограниченный перенос внутри данной площадки: обучение на `t1`, проверка на `t2` в **январе 2026** дали MAE **0.1814**, против **0.1781** при обучении на обеих турбинах. Источник: [metrics.json](../../outputs/shelek/validation/metrics.json), `leave_one_turbine_out.{train,test,fold,mae,mae_reference}`. Это не доказательство переноса на другую ВЭС с иным рельефом и оборудованием. Для новой площадки нужны данные и отдельная временная валидация.

**Учитываются ли ремонты, простои и ограничения генерации?**

Подозрительные часы недоступности помечаются и исключаются из обучения погодной зависимости. Будущие простои и диспетчерские ограничения модель отдельно не прогнозирует; для эксплуатационного графика нужен план доступности оборудования. MAE на сутках вперёд по всем валидным часам составляет **0.1680**, только по часам доступности также **0.1680** при точности записи текущего отчёта. Источник: [metrics.json](../../outputs/shelek/validation/metrics.json), `by_product.day_ahead.model.mae`, `by_product_available_hours_only.day_ahead.model.mae`. Это сравнение не доказывает способность предсказывать аварии.

**Как масштабировать и что ещё требуется до эксплуатации?**

Турбины и площадки задаются конфигурацией; погода загружается по площадке, модель обучается на площадку, а LLM вызывается на выпуск. Но работа на большом парке и нагрузочные характеристики пока не подтверждены. Следующие шаги — поток SCADA, оркестрация обновлений, реестр моделей, мониторинг дрейфа, учёт доступности турбин и корректная агрегация портфельной неопределённости. Для коммерческого использования нужно отдельно решить условия погодного API и защиту интерфейса.

**Какое главное ограничение вы сами считаете существенным?**

Нет факта тестового периода, проверена только одна площадка, а интервалы прошли ограниченную временную проверку. Сложный рельеф, редкие экстремумы и будущие простои остаются источниками ошибки. Поэтому мы показываем воспроизводимый прототип с измеренным историческим качеством, а финансовый эффект и эксплуатационную надёжность предлагаем проверять в пилоте.
